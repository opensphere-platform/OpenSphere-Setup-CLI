Local implementation candidate, 2026-09-10. This is not a deployment or clean-install acceptance report.

The Console's independent Knowledge worker now has conditional installation-record adapters. Its scoped completion receipt uses `opensphere.knowledge-installation/v1` with `scope=knowledge-component` and `runtimeState=NotObserved`. Setup packages the same contract and conformance fixture (build-time sync: Console `scripts/sync-knowledge-installation.mjs --setup-root <Setup checkout>`, with `--check` for validation). This is not a runtime sibling-source dependency.

`verifyInstallation` may use the receipt's historical Beszel bootstrap proof only for the identical hub/agent/bootstrap image digests. It still performs fresh runtime checks. The receipt does not assert `runtimeImagesMatchLock` for the full Console; unknown schemas, stale observations and mismatched operation/state/version/hash are rejected. Installing is written after delivery and Ready only after matching current activation/search. A lost completion reply is recovered by re-observing the same operation. This code has not enabled the current C_API server worker or granted its runtime permissions.

Normal Setup verifies the Console release under its existing channel trust policy before preparing manifests. When that exact Console source revision declares the Knowledge volume slot, Setup reads `apps/osaa-gateway/knowledge-bundle/lock.json` at the **same source revision**, never from a mutable branch. The pointer pins the separate Knowledge repository, full source commit, content version, bundle hash and GHCR image digest. `doctor`, installation and component upgrade use the same materializer before applying resources. Private artifact reads use the existing caller-supplied registry credential; it is not put in a ConfigMap or migrated into another credential store.

`src/knowledge-artifact.mjs` reads only the fixed GHCR Knowledge repository. Manifest/index, config, compressed layer and uncompressed layer digests are checked. The image must contain one data layer, no command/entrypoint, the expected source commit and governed build metadata. The OCI build version is the OS 12-digit build number; the bundle's `knowledge-v...` content version is checked separately. Existing localhost edge authority is not a cryptographic signature. The normal Console release verification establishes the admitted pointer; this code does not introduce a new signing key or accept a chat-provided pointer as trusted.

The `tar-stream` dependency is pinned because Node has no built-in tar decoder and hand-writing one adds avoidable parsing risk. The parser never extracts files to disk. Only the regular file `knowledge/bundle.json` and its parent directory are admitted; additional files, links, duplicate entries, malformed archives and oversized input fail. A GHCR blob redirect may go only to its fixed HTTPS GitHub container CDN, without Authorization. The image is never run and Docker is not needed by the materializer.

Verified bytes are divided into 128-KiB binary parts and immutable ConfigMaps under `opensphere-console`. A separate small ConfigMap contains the pointer and ordered part hashes. Each object stays below Kubernetes's 1-MiB ConfigMap bound and the 256-KiB client-side-apply annotation bound; the complete bundle remains bounded to 4 MiB. Gateway receives one read-only projected volume at `/var/run/opensphere-knowledge`. It reconstructs and verifies the exact bytes through the same versioned package contract before seeding the existing Supabase index. No Secret, service, sidecar, PVC, database or RBAC scope is added. The common package contract is published by Console and packaged in Setup; runtime code does not read sibling source checkouts.

The Gateway image no longer copies a Knowledge image at build time. A changed package can therefore be delivered using data and a volume-reference rollout while retaining the Gateway image. The complete release lock may also contain the admitted `knowledge` pointer and a component transition declares `changedKnowledge:true`. Both fields participate in the same release digest. An independent update preserves all images and the Console source revision; knowledge provenance remains separate. Both Console and Setup reject hidden changes, removal, same-version replacement and downgrade. A later code update inherits the installed pointer. When a pointer is recorded it takes precedence over the older Console source pointer, and an unsupported Gateway manifest fails before mutation.

Normal upgrade selects the unchanged Gateway manifest, prepares both target and recovery data, persists the pointer and complete resource inventory, and verifies the selected rollout. Retrying an exactly identical installed target verifies without reapplying it; changed metadata under the same digest fails. `verifyKnowledgeDelivery` checks immutable live ConfigMap bytes, part hashes, current rollout and the mounted sources/read-only mode of every current Gateway Pod. It returns delivery evidence, explicitly not database activation or vector search success. Missing recorded provenance remains `NotRecorded`, not verified delivery. Deployment rollback restores files/pointer only; a newer active DB baseline cannot be overwritten by an old Pod and needs separate owner verification or a forward corrective release.

**The current C_API still lacks an active Platform Release executor; 22/Shell release discovery/execution, actual activation/search verification and clean reinstall remain unfinished.** Target generation is intent, not installation. Do not substitute the retired backend or an unrecorded workstation command. Normal Setup retirement checks Pods and active ReplicaSets, defers deletion while a reference remains and keeps deferred objects in the installation inventory across upgrade/rollback for the next cleanup attempt.
